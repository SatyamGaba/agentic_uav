Lesson 2 — agentic_uav

The SwarmMethod seam

Beat 4, up close: how one observation becomes an action — and why the harness can't tell which method it's running.

Mission link. Swappability isn't a convenience feature — it's evidence. If the harness literally cannot branch on which method is active, then no reviewer can claim the engine was rigged to favour agentic. This lesson hands you that argument in code.

Recall: where we are

In Lesson 1, six of the seven beats in a tick were identical for every method; only beat 4 — decide varied. That beat is a single call to a SwarmMethod. Today we open it.

The contract: three methods, nothing more

SwarmMethod is a Protocol policy.py:20 — structural typing, so there's no base class to inherit. A class is a method if it has these three members:

method_id: str
Its name ("static", "greedy", "agentic", …).
initialize_mission(simulation) → MethodState
Build the method's private memory once, before the run. Called at construction time.
decide_tick(simulation, observations, method_state) → list[Action]
The heart of beat 4: turn the per-UAV observations into a list of Actions.
handle_event(event, method_state) → None
React to a fired disruption (baselines no-op; agentic arms a re-plan).

Every one of the five methods implements exactly this surface — all in policy.py, not one file each. That's the whole interface a method must satisfy.

The single swap point

There is exactly one place in the entire decision path where a method name becomes a method object:

# policy.py:468
def build_method(method_name: str) -> SwarmMethod:
    methods = {
        "static":             StaticPartitionMethod(),
        "rules":              RuleAdaptiveMethod(),
        "task_consideration": TaskConsiderationMethod(),
        "greedy":             GreedyMethod(),
        "agentic":            AgenticMethod(decider=build_decider()),  # LLM wired here
    }
    return methods[method_name]

Run the proof yourself — search the harness for the string that selects a method:

$ grep -rn "method_name" agentic_uav/simulation.py
simulation.py:149:  return cls(config, build_method(config.method_name))
# …and nowhere else. The simulator names a method exactly once.

The harness is method-blind

After construction, Simulation holds the method as an opaque self.method and only ever calls the three contract members. It never asks which method it is — no isinstance, no if method_name == …:

# simulation.py — the only three places the method is touched per run
self.method_state = self.method.initialize_mission(self)        # :143
...
    self.method.handle_event(event, self.method_state)          # :177
...
actions = self.method.decide_tick(self, observations, ...)     # :197
The swappability invariant. Changing config.method_name is sufficient to swap the entire decision layer — and nothing else in the codebase branches on the method. The world, comms, sensing, and metrics can't behave differently for agentic because they never learn it's running. CLAUDE.md states this as a hard invariant.

Trace one observation through the seam

  1. config.method_name = "agentic" → Simulation.from_config calls build_method("agentic") simulation.py:149
  2. → returns AgenticMethod(decider=build_decider()); default decider is the deterministic MockAgentDecider policy.py:476 · llm_agent.py
  3. → initialize_mission returns MethodState(replan_pending=True) — the only method that arms a re-plan up front policy.py:222
  4. Each tick, beat 3 builds observations[uav_id] = {self, nearby, known_urgent, messages} → handed to decide_tick
  5. → decide_tick returns a list[Action]; each Action carries target_cell, new_role, messages planning.py
  6. → beat 5 (resolve_actions) consumes those actions — identically, whatever method produced them.

Swap step 1 to "greedy" and only steps 2–3 change shape; steps 4–6 are byte-for-byte the same path. That is the seam doing its job.

Same shape, different reasoning — and different memory

Every method receives the same observations and the same MethodState type. They diverge only in which fields of that shared memory they populate:

A defense point: the complexity inversion

An older audit (report.md) found the proposed method was the simplest of all — a 15-line nearest-cell picker. That finding is now stale. By line count in policy.py today:

Method≈ linesDistinctive machinery
greedy18none — it's the fallback
rules60peer-conflict avoidance
task_consideration70scoring, hysteresis, commitments
agentic180replan/execute split, in-tick deconfliction, plan persistence
Now the largest, most structured method. agentic is the only one with an event-triggered re-plan, a persisted plan it executes between events, and synchronous in-tick negotiation to deconflict colliding targets. If a reviewer cites the old "it's the simplest method" critique, you can open policy.py:211–390 and show the opposite.
But be precise — and honest. That 180 lines is orchestration, not yet smarter per-UAV reasoning. The actual choice is delegated to the decider, and the default MockAgentDecider still mirrors greedy. So today the seam, the re-plan cadence, and the negotiation are real; the "intelligence" is pluggable and currently mocked. The honest claim is about architecture, not a measured win — exactly as we framed it in L1.
